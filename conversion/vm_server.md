# vm_server: understanding doc

Scope: the `vm_server` role, applied by `playbooks/dev_desktop.yml`. All
file:line citations are relative to `conversion/ansible/` (byte copies of
the ansible repo at 79d1ca1, hashes in `conversion/SOURCE`). Last read
against those copies on 2026-11-03. The playbook and the roles without a doc
of their own are in `conversion/dev_desktop.md`; this doc covers `vm_server`
only, so its skip list is every other role: `admin_users`, `dev_common`,
`docker`, `nvm_node`, `golang`, `rust_build`, `rust_tools`, `tmux`.

## Purpose

`vm_server` turns a workstation into a KVM/libvirt host with Vagrant
tooling. Per family it installs a long package list (KVM, libvirt, virt
tools, `ansible`, and on RedHat `ruby*` and `*-devel`) and copies a
`/usr/bin/vagrant` wrapper script that runs Vagrant inside a container
(`roles/vm_server/tasks/debian.yml:3-13`, `roles/vm_server/tasks/redhat.yml:3-13`);
then for each admin user it adds them to group `libvirt` and creates four
world-writable `.vagrant.d` directories
(`roles/vm_server/tasks/vagrant_per_user.yml:3-40`).

- Who runs it: `playbooks/dev_desktop.yml:11` (fourth of nine roles) and
  `playbooks/minikube.yml` (out of scope for this port). `admin_users` runs
  before it, so the accounts exist.
- Dispatch is by `debian_based` and `redhat_based`
  (`roles/vm_server/tasks/main.yml:2-8`); the per-user include loops over
  `admin_users` (`main.yml:10-11`, `inventories/group_vars/all:16`).
- Variables: `debian_packages_kvm` and `redhat_packages_kvm`
  (`roles/vm_server/vars/main.yml:3-37`), `vagrant_version`
  (`vars/main.yml:1`), `selinux_booleans_kvm` (`vars/main.yml:39-40`).
- The user's triage (2026-11-04) shrinks the role to KVM and libvirt plus the
  `libvirt` group; vagrant, `ansible` and `ruby*` go.

### Arch and Amazon Linux 2023

- Ansible installs nothing: neither is in `debian_based` or `redhat_based`
  (`inventories/group_vars/all:4,6`; `roles/vm_server/tasks/main.yml:2-8`
  has no other branch). The per-user include still runs and asks for group
  `libvirt` (`vagrant_per_user.yml:3-8`), which does not exist there, so the
  role fails on those two families.
- The port adds them on the distro packages: Arch `libvirt`, `qemu-base`,
  `virt-install`; Amazon Linux 2023 `libvirt`, `libvirt-client`, `qemu-kvm`

### Every host

- Each admin user is in group `libvirt`, which a package creates (below).
- `virsh --version` runs for an admin user in a login shell (client only;
  `virsh -c qemu:///system version` needs the daemon and KVM and is printed
  only, A-5b-13).
- Dropped: `/usr/bin/vagrant` (both wrappers), the four `.vagrant.d`
  directories, `ansible`, `ruby*`, `libvirt-devel`, `openssl-devel`,
  `selinux_booleans_kvm`, `vagrant_version`.

## Preserved knowledge

1. The group `libvirt` is the point of the per-user task: its comment says
   "Admin users need this group to avoid annoying GUI warnings"
   (`roles/vm_server/tasks/vagrant_per_user.yml:3`). It is what lets a user
   manage the system libvirt without root; the port keeps it.
2. The group comes from a package, not from the role: `libvirt-daemon-system`
   creates it on Debian and Ubuntu (its postinst runs `addgroup --quiet
   --system libvirt`, probe), `libvirt-daemon-common` on the RedHat family
   (its scriptlet), `libvirt` on Arch (a sysusers entry) and Amazon Linux. So
   the user op must run after the packages, and the group is not added by a
   `group` op (its name must match the package's).
3. Both package lists carry packages that serve the dropped parts or nothing:
   `ansible`, `ruby`, `ruby-devel`, `openssl-devel`, `libvirt-devel` (build
   dependencies for Vagrant plugins), `policycoreutils-python-utils` and
   `libselinux-python3` (SELinux tooling for `selinux_booleans_kvm`, which no
   task reads: `vars/main.yml:39-40` is its only mention in the repo).
4. `vagrant_version: '2.2.19'` is defined and read by no task
   (`roles/vm_server/vars/main.yml:1` is its only mention). The commented-out
   download at `roles/vm_server/tasks/main.yml:13-18` is a TODO for a
   `vagrant_tools` file with no known source.
5. The two wrappers differ by container tool and mount set (docker
   `-v ~/.vagrant.d:/.vagrant.d`; podman mounts `boxes`, `data`, `tmp`
   separately and runs `--privileged`); the four 0777 directories exist to
   serve both (`roles/vm_server/files/vagrant.docker:14-22`,
   `files/vagrant.podman:14-27`).
6. `policycoreutils-python-utils` is requested on Debian
   (`roles/vm_server/vars/main.yml:24`) and exists there; it is a SELinux tool.
7. Arch and Amazon Linux get nothing from Ansible and then fail at the group
   task (Outcomes).

| Debian 12 | same names: libvirt 9.0.0, `virtinst` 4.1.0, `bridge-utils` 1.7.1 | same virtual `qemu-kvm` |
| Rocky 9, 10 | `qemu-kvm` 10.1.0, `libvirt` 11.10.0, `libvirt-client`, `virt-install` 5.1.0 (appstream) | |
| Fedora 43 | `qemu-kvm` 10.1.5, `libvirt` 11.6.0, `libvirt-client`, `virt-install` 5.1.0 (updates) | |
| Amazon Linux 2023 | `qemu-kvm` 11.0.0, `libvirt` 12.0.0, `libvirt-client` (amazonlinux repo) | no `virt-install` package |
| Arch | `libvirt` 1:12.9.0, `qemu-base` 11.1.3, `virt-install` 5.1.0 (extra) | `dnsmasq`, `iptables-nft` are optional dependencies of `libvirt` for the default NAT network |

- Ubuntu 24.04 `qemu-kvm`: `apt-get install qemu-kvm` completes (rc 0) and
  installs `qemu-system-x86` 1:8.2.2; `dpkg -l qemu-kvm` then shows status
  `un` (not installed), so the installed name differs from the requested
  name. Ubuntu's own server page installs `qemu-kvm libvirt-daemon-system`
  and adds the user with `adduser $USER libvirt`; it does not say whether
  the system daemon starts after install.
  Source: https://ubuntu.com/server/docs/how-to/virtualisation/libvirt/ (accessed 2026-11-03)
- Group `libvirt`: after installing `libvirt-clients` alone it is absent on
  Debian 12; after `libvirt-daemon-system` it exists on Ubuntu 24.04
  (`libvirt:x:104:ubuntu`) and Debian 12 (`libvirt:x:108:`). On the RedHat
  family it exists after `libvirt-daemon` (created by the
  `libvirt-daemon-common` scriptlet on Rocky 10), on Fedora 43, Rocky 9 and
  10, and Amazon Linux 2023; on Arch after `libvirt` + `qemu-base` (sysusers
  entry in `/usr/lib/sysusers.d/libvirt.conf`, owned by `libvirt`).
- `virsh --version` after the kept packages: 10.0.0 (Ubuntu 24.04), 9.0.0
  (Debian 12), 11.10.0 (Rocky 10), 12.0.0 (Amazon Linux 2023), 12.9.0 (Arch).
- Open: `docker run --rm ubuntu:24.04 sh -c 'apt-get update -qq && apt-get install -y -qq qemu-kvm && dpkg -l qemu-system-x86 qemu-kvm'` shows the installed name (run 2026-11-03: `qemu-system-x86` is `ii`, `qemu-kvm` is `un`); the VM gate's second pass (`CHANGED 0`) settles whether `pkg` counts the virtual name as installed.
- Verdict: the kept names resolve on every family the port covers, with the
  virtual-name caveat on Debian and Ubuntu.

### Daemon start per family (Q D2, "the same for libvirt")

Probe 2026-11-03, after installing the kept packages in a container,
`systemctl is-enabled` per unit:

| Family | Result |
|---|---|
| Ubuntu 24.04, Debian 12 | `libvirtd.socket` and `libvirtd.service` enabled |
| Fedora 43, Rocky 10 | `virtqemud.socket` and `virtqemud.service` enabled (the preset enables them: `enable virtqemud.service`, `enable virtqemud.socket`); `libvirtd.*` disabled |
| Amazon Linux 2023 | `virtqemud.socket` and `virtqemud.service` disabled; no `libvirtd` units exist |
| Arch | `libvirtd.socket`, `libvirtd.service`, `virtqemud.socket`, `virtqemud.service` all disabled |

- libvirt's daemon page: under systemd the daemons use socket activation,
  "There is no need to start the services as they will get started when the
  first socket connection is established", once the `.socket` units are
  enabled (`virtqemud.socket` for the modular daemons, `libvirtd.socket` for
  the monolithic one). The RPC client still prefers the monolithic `libvirtd`
  for now.
  Source: https://libvirt.org/daemons.html (accessed 2026-11-03)
- Verdict: the Debian family and the Fedora/EL family leave the daemon
  enabled; Amazon Linux 2023 and Arch do not, so those two need `systemctl
  enable --now` on a socket unit (a marked `sh!` hack, `// HACK(svc)`, D2).
  A container has no running systemd, so "enabled" is the unit state, not
  proof that the service answers.
- Open: on an `amazonlinux:2023` VM, `dnf -y install libvirt qemu-kvm libvirt-client && systemctl enable --now virtqemud.socket && virsh -c qemu:///system version` shows whether the modular socket is the unit to enable there.
- Open: on an Arch VM, `pacman -S --noconfirm libvirt qemu-base && systemctl enable --now libvirtd.socket && virsh -c qemu:///system version` shows whether the monolithic socket is the unit to enable there.
- Open: on a `rockylinux/rockylinux:10` VM, `dnf -y install libvirt qemu-kvm libvirt-client && systemctl is-active virtqemud.socket` shows whether the install also started the socket.

### Vagrant and the wrappers

- Verdict: dropped by the user's triage; there is no vendor method to compare

## Recommendation and decision

### Options

1. Keep the role as is (packages, wrappers, `.vagrant.d`). For: no change.
   Against: installs `ansible` and `ruby` on a workstation, two world-writable
   executables and directories, nothing on Arch and Amazon, and a failing
   group task there.
2. Shrink to KVM/libvirt and the `libvirt` group. For: matches the user's
   triage and the VM check (`virsh --version`, group membership); smaller
   plan; works on Arch and Amazon Linux 2023. Against: anyone who used the
   Vagrant wrappers loses them.
3. Shrink further to the group alone. For: smallest. Against: the group is
   created by a package, so the role needs the packages anyway.

### Position

Option 2, with the package sets in Outcomes: Debian family `qemu-kvm`,
`libvirt-daemon-system`, `libvirt-clients`, `virtinst`, `bridge-utils`;
RedHat family `qemu-kvm`, `libvirt`, `libvirt-client`, `virt-install`;
Arch `libvirt`, `qemu-base`, `virt-install`; Amazon Linux 2023 `qemu-kvm`,
`libvirt`, `libvirt-client`. Each admin user then joins `libvirt` after the
packages. Dropped, besides the vagrant files: `python3-libvirt`,
`libnss-libvirt`/`libvirt-nss`, `libguestfs-tools`, `virt-top`,
`virt-manager`, `genisoimage`, `policycoreutils-python-utils`,
`libselinux-python3`, `qemu-utils`/`qemu-img` as separate requests (the
`qemu-kvm` request pulls `qemu-utils` on Ubuntu, probe). Stakes: a user who
needs `virt-manager` or `virt-top` installs it by hand; with the full list
kept the plan carries 14 to 18 packages for a role whose proof is `virsh
--version`.

Question for the reviewer. Situation: the user's triage names what is
dropped (vagrant dirs, wrappers, `ansible`, `ruby*`, `selinux_booleans_kvm`,
`vagrant_version`) and what stays ("KVM and libvirt, daemon and clients,
virt-install, bridge utils"); the YAML also installs `virt-manager`,
`virt-top`, `libguestfs-tools`, `genisoimage`, the python and nss libvirt
bindings and the SELinux python tools. Options: (a) drop those as well,
keeping only the named set; (b) keep the virt tools as the YAML lists them
and drop only the vagrant, ansible, ruby, devel and SELinux items. Position:
(a), since `virsh` and the group are the proof and the list was written for
the Vagrant workflow. Stakes: with (b) the plan carries the extra virt tools
and bindings on every family that has them, and the Debian list keeps
`virt-manager` (a GUI) on a host that may have none; with (a) a workstation
that wants `virt-manager` installs it by hand.

Dropped branches (no image reaches them): the vagrant wrappers and
`.vagrant.d` directories.

Bugs the oracle cannot see (fixed in the port): the 0777 on
`/usr/bin/vagrant` and `.vagrant.d` (gone with them); the group task failing
on Arch and Amazon (the port installs the packages that create the group
there); `ansible` and `ruby*` installed on every workstation (gone).

Intended differences (bugs fixed in the port that the oracle sees): none; no
Ansible baseline exists for the shrunk role.

Primitive gaps: `svc` for the libvirt socket on Arch and Amazon Linux 2023:
marked hack (`// HACK(svc)`, D2), since a service primitive is a non-goal.

Built-primitive defects: the virtual package name `qemu-kvm` on the Debian
family may not read as installed (Open above); until the VM gate answers it,
the port requests `qemu-kvm` and keeps the check in the gate.

Decision: vm_server shrink to KVM/libvirt and the `libvirt` group (vagrant, `ansible`, `ruby*` dropped). Decided by the user 2026-11-04 (triage); levels not yet reviewed.
