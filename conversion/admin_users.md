# admin_users: understanding doc

Scope: the `admin_users` role, applied by `playbooks/dev_desktop.yml`. All
file:line citations are relative to `conversion/ansible/` (byte copies of
the ansible repo at 79d1ca1, hashes in `conversion/SOURCE`). Last read
against those copies on 2026-11-03. `conversion/dev_desktop.md` covers the
playbook and the roles without a doc of their own; this doc is the ten
levels for `admin_users` only, so its skip list is every other role:
`dev_common`, `docker`, `vm_server`, `nvm_node`, `golang`, `rust_build`,
`rust_tools`, `tmux`.

## Purpose

`admin_users` makes the people who administer a workstation able to use
`sudo` without a password. It edits two lines of `/etc/sudoers`, then for
each user in `admin_users` makes sure the account exists with a shell, is in
the sudo group, has a `~/.ssh` directory and has a drop-in file in
`/etc/sudoers.d` (`roles/admin_users/tasks/main.yml:3-20`,
`roles/admin_users/tasks/per_user.yml:3-42`).

- Who runs it: `playbooks/dev_desktop.yml:8`, first of nine roles, as root.
  No other playbook applies it (`git grep` over `playbooks/` at 79d1ca1).
- Who else reads its list: `docker` (`roles/docker/vars/main.yml:2`),
  `golang` (`roles/golang/tasks/main.yml:8`) and `vm_server`
  (`roles/vm_server/tasks/main.yml:11`) loop over the same `admin_users`,
  and they run after it, so the accounts exist by then.
- Where the variables are: `admin_users: ["{{ ansible_user }}"]`
  (`inventories/group_vars/all:16`), `default_password: ""`
  (`inventories/group_vars/all:26`), the distro flag `redhat_based`
  (`inventories/group_vars/all:4`).

## Outcomes

### Debian family (Ubuntu, Pop!_OS, Debian; `debian_based`, `inventories/group_vars/all:6`)

- `/etc/sudoers` holds the line `#includedir /etc/sudoers.d`
  (`roles/admin_users/tasks/main.yml:6`) and the line `Defaults    secure_path =
  /sbin:/bin:/usr/sbin:/usr/bin:/usr/local/bin:/usr/local/sbin`
  (`main.yml:14`), each written through `/usr/sbin/visudo -cf` (`main.yml:9,17`).
- For each admin user: the account exists with shell `/bin/bash` when the run
  created it (`roles/admin_users/tasks/per_user.yml:3-17`); member of group
  `sudo` (`per_user.yml:24`, `append: yes`, `:25`); `/home/<u>/.ssh` mode 0700
  owned by `<u>:<u>` (`per_user.yml:27-33`); `/etc/sudoers.d/<u>` mode 0440,
  `root:root` (`per_user.yml:35-42`) with the three lines of the template.

### RedHat family (CentOS, RedHat, Fedora, Rocky, AlmaLinux; `redhat_based`, `inventories/group_vars/all:4`)

- The same, with the group `wheel` instead of `sudo` (`per_user.yml:24`).

### Amazon Linux and Arch

- The flag `redhat_based` omits `Amazon` and `Archlinux`
  (`inventories/group_vars/all:4`, `arch_based` at `:5` is never read by this
  role), so the role asks for group `sudo` there (`per_user.yml:24`). That
  group does not exist on either (Local probes), so the group task fails.

### Every host

- The drop-in `/etc/sudoers.d/<u>` has exactly these three lines
  (`roles/admin_users/templates/sudoers_template.j2:1-3`):
  `<u> ALL=(ALL)       NOPASSWD: ALL` (seven spaces after `(ALL)`),
  `Defaults:<u> !requiretty`, `Defaults:<u> !env_reset`.
- The password field of a user the run created: `default_password`, which is
  `""` (`inventories/group_vars/all:26`). Observed, the field is not changed
  (see Is the method current).
- No `authorized_keys` content: the role creates `~/.ssh` and nothing in it.

## Preserved knowledge

1. Both sudoers edits are validated with `visudo -cf %s` before the file is
   replaced (`roles/admin_users/tasks/main.yml:9,17`); a bad line never lands
   in the live file. The port must validate too, or a typo locks everyone out
   of sudo.
2. `#includedir` is a directive, not a comment: sudo treats `#includedir` and
   `#include` as directives despite the `#` (sudoers manual, Source below).
   That is the spelling every sudo version reads, including those before
   1.9.1; the port must not lose it where `@includedir` is absent.
3. The user list is a variable and the role loops (`main.yml:19-20`); each
   user gets an independent drop-in named after them
   (`per_user.yml:37`), so one user can be removed without touching others.
4. The shell and password are set only for a user the run created
   (`per_user.yml:18`). A user that already exists keeps their shell.
5. `/home/{{ item }}/.ssh` is built from the name, not from the user's
   account home (`per_user.yml:31`); it matches only where homes live in
   `/home`.
6. The drop-in has `Defaults:<u> !env_reset` (`sudoers_template.j2:3`): the
   user's environment passes through `sudo` unchanged.
7. Group `wheel` on `redhat_based`, `sudo` otherwise (`per_user.yml:24`);
   `redhat_based` lists CentOS, RedHat, Fedora, Rocky and AlmaLinux only
   (`inventories/group_vars/all:4`).
8. The second include line is idempotent once added: on the next run the
   regexp `^#includedir` matches the appended line, so no third line appears
   (observed 2026-11-03, see Is the method current).

## Is the method current

Research date: 2026-11-03.

### The `@includedir` form

- sudo's manual: `@includedir` is the current directive; `#include` and
  `#includedir` are accepted for compatibility with sudo versions before
  1.9.1, and a `#` before an include directive does not make it a comment.
  Source: https://www.sudo.ws/docs/man/sudoers.man/ (accessed 2026-11-03)
- Ansible's `lineinfile` with `state: present` and a `regexp` that matches
  nothing adds the line, at end of file when no `insertafter` is given; when
  the regexp matches, the last matching line is replaced.
  Source: https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/lineinfile_module.html (accessed 2026-11-03)
  (The shorter URL `https://docs.ansible.com/ansible/latest/collections/ansible/builtin/lineinfile_module.html` answered HTTP 429 on 2026-11-03 and was not retried.)
- Verdict: current sudoers files written by Debian, Ubuntu and Arch use
  `@includedir`, so `^#includedir` matches nothing there and Ansible appends
  `#includedir`. Fedora, Amazon Linux 2023 and the EL family still ship
  `#includedir`; there the regexp matches and nothing is added.

### Ansible bugs found

1. **`^#includedir` misses `@includedir`.** Observed 2026-11-03 with
   ansible-core 2.21.6 in `ubuntu:24.04`: after the task `/etc/sudoers` holds
   `57:@includedir /etc/sudoers.d` and `58:#includedir /etc/sudoers.d`
   (`changed: true`, `"msg": "line added"`). Both lines are valid, so sudo
   reads the directory twice and nothing breaks, but every drop-in is read
   twice.
2. **`secure_path` replaces the distro's line.** Observed in the same run: the
   Ubuntu line `Defaults	secure_path="/usr/local/sbin:...:/bin:/snap/bin"`
   became `Defaults    secure_path = /sbin:/bin:/usr/sbin:/usr/bin:/usr/local/bin:/usr/local/sbin`.
   `/snap/bin` is gone, the `/usr/local` directories moved behind the system
   ones, and on Fedora 43 and Amazon Linux 2023 the entry
   `/var/lib/snapd/snap/bin` is lost the same way (probe table). On the EL
   family, whose line is `/sbin:/bin:/usr/sbin:/usr/bin`, and on Arch
   (`/usr/local/sbin:/usr/local/bin:/usr/bin`) the new line only adds
   directories.
3. **`password: ""` does not set an empty password.** `per_user.yml:17` passes
   `default_password`, which is `""` at 79d1ca1. Observed 2026-11-03: with
   ansible-core 2.21.6 on `ubuntu:24.04` the module reports `changed` for the
   shell but the `/etc/shadow` field stays `!` (`passwd -S` letter `L`), and
   with ansible-core 2.15.13 on `rockylinux:9` on an existing user it reports
   `"changed": false` and the field stays `!!` (`LK`). So the task does not
   give a new user an empty password field; it does nothing. This is
   different from what the roadmap assumed (an empty field, `passwd -S` letter
   `NP`). A plain `usermod -p ""` does give `NP` (probe table), so the
   difference is in the module.
4. **Group `sudo` on Arch and Amazon Linux.** `per_user.yml:24` picks `wheel`
   only for `redhat_based`, which omits both. Observed: `"msg": "Group sudo
   does not exist"` on `archlinux` with ansible-core 2.22.0 (and the same text
   on `rockylinux:9`, where the group is also absent). The role cannot run on
   those two families.

- The roadmap's note that Rocky 9 and 10 ship `@includedir` is not what the
  images show: the EL family ships `#includedir`. The bug 1 set is Ubuntu,
  Debian and Arch.
- `ubuntu:26.04`'s `visudo` is sudo-rs's: `visudo -cf /etc/sudoers` prints
  `parsed OK`, and `visudo -cf` accepts a file with `#includedir` appended
  (rc 0), so the `validate` command works there.
- `usermod -p ""` on `ubuntu:24.04`: shadow field empty, `passwd -S` letter
  `NP`.
- Group `sudo` after installing sudo: present on Ubuntu and Debian, absent on
  Rocky, Fedora, Arch, Amazon Linux 2023.

Open: `docker run --rm amazonlinux:2 sh -c 'yum -y -q install sudo >/dev/null && grep -n -E "includedir|secure_path" /etc/sudoers'` for Amazon Linux 2 (the playbook mentions it, no image here builds it).
Reproduce (run on 2026-11-03, results in the table): `docker run --rm ubuntu:24.04 sh -c 'apt-get update -qq && apt-get install -y -qq sudo && grep -n includedir /etc/sudoers'`, `docker run --rm rockylinux/rockylinux:10 sh -c 'dnf -y -q install sudo && grep -n includedir /etc/sudoers'`, `docker run --rm debian:12 sh -c 'apt-get update -qq && apt-get install -y -qq sudo && grep -n includedir /etc/sudoers'`, `docker run --rm fedora:43 grep -n includedir /etc/sudoers` and `docker run --rm archlinux sh -c 'pacman -Sy --noconfirm sudo >/dev/null && grep -n includedir /etc/sudoers'`; the stock images need the install step first.

## Recommendation and decision

### Options

1. Port both sudoers edits and the user tasks exactly as the YAML says
   ("port as is"). For: the oracle shows no sudoers difference and the
   port is provably what Ansible did; the skill's equivalence-first rule.
   Against: the port carries bugs 1 and 2 (a double include on Ubuntu,
   Debian and Arch; the lost `/snap/bin`).
2. Fix the two sudoers bugs in the port (`^[#@]includedir` or the host's own
   spelling; `secure_path` that keeps the distro's entries). For: no
   duplicate include, no lost `snap` directory. Against: the oracle then
   shows a sudoers difference that must be declared as intended.
3. Drop the sudoers edits and keep only the drop-ins. For: smaller. Against:
   the drop-in is read only if the include exists, and the `secure_path` edit
   is the only place the role sets sudo's search path.

### Position

Option 1. The role is kept as is (the user's triage); the two sudoers fixes
wait until after equivalence so a divergence in the oracle's diff is always
a port bug.

Dropped branches (no image reaches them): none; Amazon Linux and Arch hit
the `sudo` group failure (bug 4), so the port gives them `wheel` (see the
question).

Bugs the oracle cannot see (fixed in the port): bug 3 is not a bug the port
has to fix, because the Ansible task does nothing with an empty
`default_password`; the port leaves the new account locked, which is what the
module leaves. Bug 4: the port picks `wheel` for any family that has no
`sudo` group.

After equivalence (change what the oracle sees; not made yet): bug 1 (use
`^[#@]includedir`, or write the spelling the file already uses) and bug 2
(keep the distro's `secure_path` entries and put `/usr/local` first). Both
are recorded here and declared as intended differences when they land.

Primitive gaps: none beyond the new `user` and `file(..).validate(..)`
primitives that this goal builds first (see Task intent).

Built-primitive defects: none known.

Question for the reviewer. Situation: Arch and Amazon Linux 2023 have group
`wheel` and no group `sudo`, and Ansible's role asks for `sudo` there (bug
4). Options: (a) `wheel` on every family without a `sudo` group, so the role
works everywhere; (b) port exactly, failing on those two families as Ansible
does. Position: (a). Stakes: with (b) a new Arch host cannot be configured;
with (a) the port diverges from Ansible only where Ansible cannot run, so no
oracle image sees it.

Decision: keep (port as is, both sudoers edits exactly as the YAML says; the fixes are recorded under "After equivalence"). Decided by the user 2026-11-04 (triage); levels not yet reviewed.
