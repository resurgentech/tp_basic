# docker: understanding doc

Scope: the `docker` role, applied by `playbooks/dev_desktop.yml`. All
file:line citations are relative to `conversion/ansible/` (byte copies of
the ansible repo at 79d1ca1, hashes in `conversion/SOURCE`). Last read
against those copies on 2026-11-03. The playbook and the roles without a doc
of their own are in `conversion/dev_desktop.md`; this doc covers `docker`
only, so its skip list is every other role: `admin_users`, `dev_common`,
`vm_server`, `nvm_node`, `golang`, `rust_build`, `rust_tools`, `tmux`.

## Purpose

`docker` puts Docker Engine on a workstation and lets the admin users run
it. The role is a dispatcher over a Galaxy role: on the Debian family it
includes `geerlingguy.docker` after overriding facts for Pop!_OS
(`roles/docker/tasks/debian.yml:3-13`); on the RedHat family it overrides
the facts to `RedHat`, removes `podman` and `runc`, and includes the same
Galaxy role (`roles/docker/tasks/redhat.yml:3-21`). The role's only variable
is `docker_users: "{{ admin_users }}"` (`roles/docker/vars/main.yml:2`).

- Who runs it: `playbooks/dev_desktop.yml:10` (third of nine roles) and
  `playbooks/minikube.yml` (first role; out of scope for this port).
- Order matters: `admin_users` runs first, so the accounts in `docker_users`
  exist (`playbooks/dev_desktop.yml:8,10`).
- The Galaxy role is `geerlingguy.docker`, listed with no version in
  `tools/scripts/requirements.yml` of the ansible repo (not mirrored), and
  its code is not in the repo. What this doc knows of it comes from its
  README: `docker_users` is "a list of system users to be added to the
  `docker` group", the service is started and enabled by default, the
  Docker repository is added by default, and `docker-compose-plugin` is
  installed by default. The README lists no Rocky or Alma support.
  Source: https://github.com/geerlingguy/ansible-role-docker (accessed 2026-11-03)
- The task dispatch is by `debian_based` and `redhat_based`
  (`roles/docker/tasks/main.yml:3-9`); the flags are in
  `inventories/group_vars/all:4,6`.

## Outcomes

The end state the port aims at (the Galaxy role is not readable, so this is
the intent, not a copy of what it did).

### Ubuntu, Pop!_OS and Debian (apt)

- apt source: `/etc/apt/sources.list.d/docker.sources` (deb822) with
  `URIs: https://download.docker.com/linux/<ubuntu|debian>`, `Suites` the
  release codename, `Components: stable`, `Signed-By:
  /etc/apt/keyrings/docker.asc`.
- Key: `/etc/apt/keyrings/docker.asc`, an armored key apt reads directly.
- Packages: `docker-ce`, `docker-ce-cli`, `containerd.io`,
  `docker-buildx-plugin`, `docker-compose-plugin`.
- The group `docker` exists (the `docker-ce` package creates it); every admin
  user is a member.
- The daemon runs and starts at boot (the package does both on this family).

### Fedora (dnf)

- Repo file `docker-ce.repo` from `download.docker.com/linux/fedora/`; the
  same five packages; group `docker` (created by the package); admin users in
  it; the daemon started and enabled by `systemctl enable --now docker`,
  which the package does not do.

### Rocky and Alma (dnf)

- As Fedora, with the repo from `download.docker.com/linux/rhel/`
  (A-5b-6, and the same path the Ansible role used through its
  `ansible_distribution='RedHat'` override, `roles/docker/tasks/redhat.yml:3-5`).

### Arch and Amazon Linux 2023 (distro package)

- The distro's `docker` package (Docker's repositories do not list either
  platform). Group `docker` exists after install; admin users in it; daemon
  handling per the table in Is the method current.
- Ansible did nothing on these two: `docker/tasks/main.yml` has branches for
  `debian_based` and `redhat_based` only (`roles/docker/tasks/main.yml:3-9`),
  and neither flag is true for Amazon or Arch (`inventories/group_vars/all:4,6`).

### Every host

- `docker run --rm hello-world` works for an admin user in a login shell.
  The `docker` group "grants root-level privileges to the user"
  (Docker's post-install page), which is why only `admin_users` get it.
- No `podman` or `runc` removal (Position).
- `get.docker.com` is not used (Is the method current).

## Preserved knowledge

1. Pop!_OS takes Docker's Ubuntu repository
   (`roles/docker/tasks/debian.yml:3-5`). The port keeps this as a mapping
   of the distro to the repo path `ubuntu`. The suite is the codename:
   Docker's Ubuntu page uses `${UBUNTU_CODENAME:-$VERSION_CODENAME}`, so a
   derivative reports its Ubuntu base.
2. Every `redhat_based` host got the `rhel` repository, Fedora included
   (`roles/docker/tasks/redhat.yml:3-5`). The port splits it: Fedora
   `fedora`, Rocky and Alma `rhel` (A-5b-6).
3. `docker_users` is `admin_users` (`roles/docker/vars/main.yml:2`): the
   people with passwordless sudo are the people with the docker group, which
   is root-equivalent anyway.
4. The role removes `podman` and `runc` first on RedHat
   (`roles/docker/tasks/redhat.yml:11-17`). Docker's RHEL page lists both in
   its removal command; the probes show the install succeeding without it.
5. The Debian-family branch has no pin and no package list in this repo: it
   is the Galaxy role's defaults (Docker Engine, CLI, `containerd.io`,
   buildx plugin and the compose plugin).
6. The `redhat.yml:7` family override and the `debian.yml:7` family override
   are no-ops (Task intent), and the last assigns a value (`'Pop!_OS'`) that
   Ansible itself never reports as a family.
7. Ansible installs nothing on Arch and Amazon Linux
   (`roles/docker/tasks/main.yml:3-9`); the port adds both on the distro
   package, as the roadmap (T52) specifies.

## Is the method current

Research date: 2026-11-03.

### apt method (Ubuntu, Debian)

- Docker's Ubuntu page: the key is downloaded to `/etc/apt/keyrings/docker.asc` from the Ubuntu `gpg` URL
  under `download.docker.com/linux/ubuntu/`, made world-readable, then
  `/etc/apt/sources.list.d/docker.sources` is written with `Types: deb`,
  `URIs: https://download.docker.com/linux/ubuntu`,
  `Suites:` the codename taken from `${UBUNTU_CODENAME:-$VERSION_CODENAME}`,
  `Components: stable`, `Architectures:` from `dpkg --print-architecture`, and
  `Signed-By: /etc/apt/keyrings/docker.asc`; packages `docker-ce`,
  `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`,
  `docker-compose-plugin`. Supported: Ubuntu 26.10, 26.04, 24.04, 22.04.
  Source: https://docs.docker.com/engine/install/ubuntu/ (accessed 2026-11-03)
- Docker's Debian page: the same with `linux/debian` and `Suites:
  $VERSION_CODENAME`; on testing or derivatives, the matching Debian codename.
  Source: https://docs.docker.com/engine/install/debian/ (accessed 2026-11-03)
- Docker's platform table lists CentOS, Debian, Fedora, Raspberry Pi OS,
  RHEL and Ubuntu; Arch Linux and Amazon Linux are not in it, and Pop!_OS is
  not named. It says Ubuntu derivatives follow the Ubuntu instructions and
  that "Docker doesn't test or verify installation on distribution
  derivatives."
  Source: https://docs.docker.com/engine/install/ (accessed 2026-11-03)
- Local probe 2026-11-03 (throwaway containers): the method above, with no
  `gnupg` installed, runs `apt-get update` against `noble/stable` on
  `ubuntu:24.04` and `bookworm/stable` on `debian:12`, and installs the five
  packages (docker-ce 5:29.9.3, containerd.io 2.4.2); the group `docker`
  exists afterwards (created by the `docker-ce` postinst: `groupadd --system
  docker`). So an armored `.asc` key needs no `gnupg` (A-5b-9).
- Verdict: current. The apt method is the deb822 file plus the armored key,
  as A-5b-9 expected.
- Open: `grep -E 'UBUNTU_CODENAME|VERSION_CODENAME' /etc/os-release` on a
  Pop!_OS host prints the Ubuntu codename the `Suites` line must use.

### dnf method (Fedora, Rocky, Alma)

- Docker's RHEL page: `dnf -y install dnf-plugins-core`, then the repo is added
  with `dnf config-manager --add-repo` from the `docker-ce.repo` file under
  `download.docker.com/linux/rhel/`, then the five packages; "This command
  installs Docker, but it doesn't start Docker"; `systemctl enable --now docker`
  starts it and enables it at boot. Supported: RHEL 8, 9 and 10; Rocky and Alma
  are not named. The removal list includes `podman` and `runc`.
  Source: https://docs.docker.com/engine/install/rhel/ (accessed 2026-11-03)
- Docker's CentOS page: the same with `linux/centos`, CentOS Stream 9 and 10.
  Source: https://docs.docker.com/engine/install/centos/ (accessed 2026-11-03)
- Docker's Fedora page: the repo is added with the dnf5 form `dnf config-manager addrepo --from-repofile`
  from the `docker-ce.repo` file under `download.docker.com/linux/fedora/`,
  then the same five packages and `systemctl enable --now docker`; supported:
  Fedora 45, 44, 43.
  Source: https://docs.docker.com/engine/install/fedora/ (accessed 2026-11-03)
- Local probes 2026-11-03: the `rhel` repo installs `docker-ce` 29.9.3 and
  `containerd.io` 2.4.2 on `rockylinux/rockylinux:10`, `rockylinux:9` and
  `almalinux:10`; the `fedora` repo does on `fedora:43`; each creates the
  group `docker`. The repo file's `baseurl` is
  `.../linux/rhel/$releasever/$basearch/stable`. All five `download.docker.com`
  paths (`rhel`, `centos`, `fedora`, `debian`, `ubuntu`) answer 200 for `gpg`.
- Verdict: current. Rocky and Alma take the `rhel` path although Docker
  names neither; the installs above succeed.
- Open: `docker run --rm almalinux:9 sh -c 'dnf -y -q install dnf-plugins-core && dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo && dnf -y -q install docker-ce containerd.io && rpm -q docker-ce'` for Alma 9.

### `podman` and `runc` on EL

- Docker's RHEL page removes both first. Probe 2026-11-03,
  `rockylinux/rockylinux:10`: `dnf -y install podman` (podman 5.8.2 and crun;
  no `runc`), the `rhel` repo, then `dnf -y install docker-ce containerd.io
  docker-ce-cli docker-buildx-plugin docker-compose-plugin` completes with no
  conflict and `podman` is still installed afterwards. `rockylinux:9`: podman,
  `runc` and `crun` installed first; after the same install `docker-ce` and
  `containerd.io` are present, `podman` stays, and `runc` is gone (replaced
  by `containerd.io`).
- Verdict: no `pkg ... absent` is needed; `containerd.io` replaces `runc`
  and `podman` coexists (A-5b-15 holds on Rocky 9 and 10).
- The roadmap's probe form (`dnf -y install podman`, the repo, then `dnf -y install docker-ce containerd.io`) needs `dnf-plugins-core` first on this image; the probe above installed it.

### Daemon start per family (Q D2)

| Family | After install | Evidence |
|---|---|---|
| Ubuntu, Debian, Pop!_OS | running and enabled | Docker's Ubuntu and Debian pages: "The `docker` service starts automatically on Debian based distributions" |
| Fedora, Rocky, Alma | not started, not enabled | Docker's Fedora and RHEL pages ("doesn't start Docker"); `systemctl is-enabled docker` prints `disabled` on `rockylinux/rockylinux:10` after install |
| Amazon Linux 2023 | `docker.socket` enabled by preset (activates the service on first use) | `rpm -q --scripts docker` calls `systemd-update-helper install-system-units docker.service docker.socket`; `/usr/lib/systemd/system-preset/90-default.preset:270` is `enable docker.socket` |
| Arch | not enabled | the `docker` pacman package ships no install script and no preset entry (probe 2026-11-03) |

- Docker's post-install page: `sudo groupadd docker`, `sudo usermod -aG
  docker $USER`, `newgrp docker`; `systemctl enable docker.service` and
  `containerd.service` to start on boot; "The `docker` group grants
  root-level privileges to the user."
  Source: https://docs.docker.com/engine/install/linux-postinstall/ (accessed 2026-11-03)
- Docker's Ubuntu page is ambiguous about the start: it tells the reader to
  check `systemctl status docker` and start it if needed, and says the
  service starts automatically on Debian-based distributions only in the
  convenience-script section. The Debian-family row above rests on that
  sentence; the VM gate (`docker run --rm hello-world` on Ubuntu 24.04) is the
  proof.
- Arch Wiki's Docker page answered "Access Denied" (an anti-bot page) on
  2026-11-03 and was not retried; the Arch row rests on the probe only.
  Source: https://wiki.archlinux.org/title/Docker (accessed 2026-11-03)
- Amazon's AL2023 documentation says the `docker`, `containerd` and `nerdctl`
  packages are available on AL2023 and gives no start step.
  Source: https://docs.aws.amazon.com/linux/al2023/ug/install-docker.html (accessed 2026-11-03), which served the page titled "Using AL2023 in containers"
- Verdict: Fedora, Rocky, Alma and Arch need `systemctl enable --now docker`;
  Ubuntu, Debian and Pop!_OS do not. Amazon Linux 2023 starts on first use
  through the socket if the preset ran.
- Open: on an `amazonlinux:2023` VM, `dnf -y install docker && systemctl is-enabled docker.socket docker.service && docker run --rm hello-world` settles whether the hack is needed there.
- Open: on an Arch VM, `pacman -S --noconfirm docker && systemctl is-enabled docker.service docker.socket` prints what the package leaves.

### Distro `docker` package on Arch and Amazon Linux

- Arch `extra` serves `docker` 1:29.9.2-1 (probe, `pacman -Si docker`);
  Amazon Linux 2023 serves `docker` 25.0.16 from its own repository, four
  majors behind Docker's 29.x. The AL2023 package is Amazon's choice and the
  only one for that platform (Docker's repositories do not list it).
- Verdict: use the distro package on both; the version gap on AL2023 is
  recorded, not fixed.

### `get.docker.com`

- Docker's Ubuntu page says the convenience script "isn't recommended for
  production environments" and is "Only recommended for testing and
  development environments", useful "for creating a provisioning script
  tailored to your needs."
  Source: https://docs.docker.com/engine/install/ubuntu/ (accessed 2026-11-03)
- Verdict: not used. The port writes the repository and the package install
  itself, so a settled host makes no network call to a script and the plan
  shows each step.

## Recommendation and decision

### Options

1. Keep the Galaxy role (`geerlingguy.docker`). For: no rewrite. Against:
   unpinned, code not in the repo, no Rocky or Alma, cannot be a telepatch
   `pkg`/`repo` with a plan the engine can show.
2. Rewrite on Docker's own repositories with `repo` + `pkg` per family, the
   distro package on Arch and Amazon. For: the method Docker documents;
   every step visible to the optimizer; matches the user's triage. Against:
   needs the `repo` and `user`/`group` primitives and the codename fact
   first; the daemon start on four families is a marked hack until `svc`.
3. Use `get.docker.com`. For: one line. Against: Docker's page says not for
   production; an unguarded script run.

### Position

Option 2. Repo path per distro: `ubuntu` for Ubuntu and Pop!_OS, `debian`
for Debian, `fedora` for Fedora, `rhel` for Rocky and Alma (A-5b-6); the
package list `docker-ce docker-ce-cli containerd.io docker-buildx-plugin
docker-compose-plugin`; the distro `docker` package for Arch and Amazon
Linux 2023; any other distro is a trace error naming it. The daemon is
started with `systemctl enable --now docker` (marked `// HACK(svc)`) on
Fedora, Rocky, Alma and Arch, never on the Debian family; Amazon Linux 2023
waits for the Open line. Every admin user joins the `docker` group.
Stakes: with the hack missing, `docker run` fails on those four families;
with `get.docker.com` the plan loses the repo and package steps.

Dropped branches (no image reaches them): the `podman`/`runc` removal, the
two family overrides at `roles/docker/tasks/debian.yml:7` and
`redhat.yml:7`.

Bugs the oracle cannot see (fixed in the port): Fedora and CentOS got the
`rhel` repository (`roles/docker/tasks/redhat.yml:3-5`) while Docker
publishes `fedora` and `centos` ones; the `Pop!_OS` family override can never
be true; the role removed `podman` from hosts that had no conflict.

After equivalence (change what the oracle sees; not made yet): none; no
Ansible baseline exists for this role.

Primitive gaps: `svc` (enabled and running): marked hack on four families,
`// HACK(svc)` (D2), because a service primitive is a non-goal of this
goal.

Built-primitive defects: none known.

Decision: docker rewrite on download.docker.com (`repo` + `pkg` per family, distro package on Arch and Amazon, no `get.docker.com`). Decided by the user 2026-11-04 (triage); levels not yet reviewed.
