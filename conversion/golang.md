## Purpose

`golang` gives a workstation the Go toolchain and, for each admin user, the
`godoc` documentation server. It includes the Galaxy role `gantsign.golang`
(`roles/golang/tasks/main.yml:3-5`), then loops over `admin_users` to install
`godoc` with `go install` (`roles/golang/tasks/main.yml:7-8`,
`roles/golang/tasks/godoc.yml:1-29`).

- Who runs it: `playbooks/dev_desktop.yml:13`, after `vm_server` and
  `nvm_node`. No other playbook applies it (`git grep` over `playbooks/` at
  79d1ca1).
- Variables: `golang_version: '1.26.1'`
  (`inventories/group_vars/all:40`), `golang_gopath: $HOME/go`
  (`roles/golang/vars/main.yml:1`), `admin_users`
  (`inventories/group_vars/all:16`).
- The Galaxy role `gantsign.golang` is listed with no version in
  `tools/scripts/requirements.yml` of the ansible repo (not mirrored); its
  code is not in the repo. Its README lists `golang_version` (default
  `1.24.2`), `golang_install_dir` (default `/opt/go/{{ golang_version }}`), a
  tarball fetched from `https://storage.googleapis.com/golang` and verified
  against a sha256 (`golang_redis_sha256sum`, "required only for versions the
  role doesn't preconfigure"), and tested platforms Debian 11 and 12, Ubuntu
  22.04 and 24.04, Rocky Linux 9, Fedora 41 and openSUSE Tumbleweed. The README
  does not mention a `/etc/profile.d` script.
  Source: https://github.com/gantsign/ansible-role-golang (accessed 2026-11-03)

## Preserved knowledge

1. The Go version is a variable, `golang_version`, set in the inventory
   (`inventories/group_vars/all:40`, `'1.26.1'`). The port drops the pin and
   wants `Latest` (the user's triage); a workstation follows go.dev.
2. `godoc` is installed per user, in the user's login shell, because `go
   install` writes to the user's `GOPATH` (`roles/golang/tasks/godoc.yml:3-29`).
   Dropped.
3. The check and the install run through `{{ user_shell }} -lc`, so they see
   the `PATH` a login shell builds (`godoc.yml:15,26`); any Go op that runs as
   a user must use a login shell too.
4. `GOPATH` is `$HOME/go` (`roles/golang/vars/main.yml:1`), a literal
   `$HOME` that only a shell expands; it equals Go's default, so the port
   sets nothing.
5. The role depends on `admin_users` accounts existing (it loops over them);
   with godoc dropped, `golang` no longer depends on `admin_users`.
6. `gantsign.golang` installs under `/opt/go/<version>`; the port installs
   at `/usr/local/go`, the location Go's install page documents, so the old
   tree stays on a host that ran the Ansible role (nothing here removes it).

## Is the method current

Research date: 2026-11-03.

### Go's own install method

- Go's install page, Linux: "Remove any previous Go installation by deleting
  the `/usr/local/go` folder (if it exists), then extract the archive you just
  downloaded into `/usr/local`, creating a fresh Go tree in `/usr/local/go`":
  `rm -rf /usr/local/go && tar -C /usr/local -xzf go1.14.3.linux-amd64.tar.gz`.
  "Do not untar the archive into an existing `/usr/local/go` tree. This is
  known to produce broken Go installations." Add `/usr/local/go/bin` to `PATH`
  in `$HOME/.profile` or `/etc/profile` for a system-wide installation. The
  page's example archive name is outdated; the current name comes from
  go.dev/dl.
  Source: https://go.dev/doc/install (accessed 2026-11-03)
- Verdict: current. The method is "remove, then extract"; the port must
  verify the download before removing anything.

### What the source serves today (the installer row)

- `https://go.dev/VERSION?m=text` returns two lines: `go1.27.3` and `time
  2026-10-19T22:20:36Z` (the first line is the version; probe 2026-11-03).
  Source: https://go.dev/VERSION?m=text (accessed 2026-11-03)
- `https://go.dev/dl/?mode=json` returns an array of releases, newest first;
  each has `version` (`go1.27.3`), `stable` (`true`) and `files`, an array
  whose entries have `filename`, `os`, `arch`, `version`, `sha256`, `size` and
  `kind`. `kind` is `archive`, `installer` or `source`; source entries have
  empty `os` and `arch`. The Linux amd64 archive on 2026-11-03 is
  `go1.27.3.linux-amd64.tar.gz`, `kind` `archive`, sha256
  `65efbc80fdc1fa2cd2631cad5b481777a68e8725f34e89f50fc6ac714e379b40`; the arm64
  one is `go1.27.3.linux-arm64.tar.gz`, sha256
  `a06e99309dbcbdca1a8ccd2282c3ee146e55930886e26b4f1193269587165f49`. The
  default listing holds only the two currently supported releases (`go1.27.3`
  and `go1.26.10`).
  Source: https://go.dev/dl/?mode=json (accessed 2026-11-03)
- How a version is pinned: the archive name carries it
  (`go<version>.linux-<arch>.tar.gz`), under `https://go.dev/dl/`, and the
  expected hash is the `sha256` of the matching `files[]` entry. Arch names
  are `amd64` and `arm64`, so the host's `uname -m` (`x86_64`, `aarch64`) maps
  to them.
- What the tool prints for its own version: `go version go1.27.3 linux/amd64`
  from `/usr/local/go/bin/go version`; `GOTOOLCHAIN=local go version` prints
  the same. Probe 2026-11-03, `ubuntu:24.04`: the archive downloaded from
  `go.dev/dl/` matched the JSON's sha256 (`sha256sum -c` printed `OK`), and
  `/usr/local/go/VERSION` reads `go1.27.3` then the build time.
- Verdict: the VERSION page gives the latest, the JSON gives the hash, the
  archive gives the tool; a plain `curl` and `tar` host needs nothing else.

### GOTOOLCHAIN

- `GOTOOLCHAIN` selects the toolchain the `go` command runs: `local` is the
  bundled one, `<name>` a specific one, `auto` is `local+auto`, and with
  `auto` the command downloads a newer toolchain when a module's `go` or
  `toolchain` line asks for one. "The default `GOTOOLCHAIN` setting is
  `auto`"; the setting is read from the environment, then the user's `go env
  -w` file, then `$GOROOT/go.env`.
  Source: https://go.dev/doc/toolchain (accessed 2026-11-03)
- Probe 2026-11-03: `go env GOTOOLCHAIN` prints `auto` and `/usr/local/go/go.env`
  holds `GOTOOLCHAIN=auto`. So `go version` run inside a module that asks for a
  newer Go can print the downloaded toolchain's version, not
  `/usr/local/go`'s; a version probe must run `GOTOOLCHAIN=local` or outside a
  module.
- Verdict: the installed toolchain stays what the port installed; downloaded
  toolchains live in the user's module cache and are not part of this role.

### godoc

- `golang.org/x/tools/cmd/godoc` is marked: "Deprecated: godoc cannot select
  what version of a package is displayed. Instead, use
  golang.org/x/pkgsite/cmd/pkgsite."; the module version is
  `v0.1.0-deprecated`. The page says deprecated, not removed, and shows no
  install command for `pkgsite`.
  Source: https://pkg.go.dev/golang.org/x/tools/cmd/godoc (accessed 2026-11-03)
- Verdict: the row's method (`go install ...godoc@latest`) installs a
  deprecated tool. The user decided to drop it; the other reason is that the
  port has no `go install` source.

## Recommendation and decision

### Options

1. Keep `gantsign.golang` and the godoc loop. For: no rewrite. Against:
   pinned to a stale 1.26.1, unpinned Galaxy role with unreadable code, a
   deprecated tool.
2. Rewrite as a `Script` source (`pkg` with a non-distro source) wanting
   `Latest`, drop godoc. For: matches Go's documented method; the installed
   version is read from `go version` and the latest from `go.dev/VERSION`;
   the plan shows what will change. Against: a settled host makes one request
   to go.dev per run (as rustup's `Latest` does, A-5b-14); a new Go release
   upgrades hosts on the next run.
3. Rewrite wanting a pin (`golang_version`). For: reproducible. Against: the
   user chose latest; the pin was the staleness.

### Position

Option 2. The host-side installer: arch from `uname -m`, the latest version
from the first line of `https://go.dev/VERSION?m=text`, the tarball from
`go.dev/dl/`, the expected hash from the JSON entry with that filename,
`sha256sum -c`, and only on a match `rm -rf /usr/local/go` then `tar -C
/usr/local -xzf`; a mismatch fails before anything is removed. `go.sh` in
`/etc/profile.d` adds `/usr/local/go/bin`. Stakes: with a pin the host stops
following Go; without the hash check a bad download leaves no Go.

Dropped branches (no image reaches them): the godoc tasks (the `go install`
source is not built).

Bugs the oracle cannot see (fixed in the port): `ignore_errors` on the godoc
check treats a missing login shell like a missing godoc
(`roles/golang/tasks/godoc.yml:19`); the `passwd_info`/`user_shell` names
collide with `rust_build`'s. Both vanish with the godoc tasks.

Intended differences (bugs fixed in the port that the oracle sees): none; no
Ansible baseline exists for this role.

Primitive gaps: a `go install` source: not built, so `godoc` is dropped
instead of written as an unguarded `sh!`.

Built-primitive defects: none known.

Decision: golang rewrite as a `Script` source wanting Latest (install from go.dev, sha256-checked); godoc dropped (needs a `go install` source telepatch lacks, and `godoc` is deprecated upstream in favour of `pkgsite`). Decided by the user 2026-11-04 (triage); levels not yet reviewed.
